### 2.3 工作方式与追踪体系（必须沿用）

**每轮工作节奏**：

1. 用户指定工作包/批次 → 读该包计划行、关联功能、已有规格和相关 review。
2. 明确：本轮要回答的问题、明确不处理的内容、已满足的依赖、可暂记的开放项、计划输出文件。
3. 定位证据（定义、配置、行为实现、调用入口与消费者、相关 UI 流程、内容样本、跨域状态变化、demo 证据或材料缺口），**不只读名称最明显的文件**。
4. 提取行为：需求/状态/规则/可观察结果；必要时分开描述：可泛化能力 / Pokémon 具体规则 / 宿主交互与 UI / 示例内容与作者配置 / 分析建议（第 5 类不能混入"参考系统已支持的行为"）。
5. 写规格与静态场景（Given/When/Then 或 输入→预期状态变化；均标"静态推导、未运行"）。
6. 检查交界：本轮规则是否已在其他规格定义——已定义的规则引用，不复制；发现冲突时记录双方位置、证据和待解决问题，不静默覆盖。
7. 更新追踪：Feature Matrix、工作包状态、证据索引、开放问题、必要的依赖和模块地图说明；**只修改与本轮有关的内容**。
8. 停止并交付 review：不自动开始下一包；自检完成不等于外部 review 通过。

**版本与哈希纪律（重要）**：

- 版本清单：`planning/review-manifest-2026-09-19.md`（随每轮更新，保留旧→新替代关系与历史，不回写抹除；清单本身不做自哈希，最终摘要给实测值）。
- 送审前/修订后都对相关文件计算 **SHA-256（shasum -a 256）+ 字节数（`stat -f "%z"` 实测）**，写入 manifest；外部 review 按「文件 + 哈希前缀 + 行号」引用。**禁止凭哈希前缀推补完整值；禁止凭记忆填写字节数**（本项目已有两次此类错误记录，均以实测修正）。
- 被审哈希与新哈希分开记录；**新哈希不伪称为复审对象**。
- 状态回填（Reviewed）只做管理性变更：被审哈希保留于历史，回填后新哈希为管理性变更。
- 外部 review 原件一律复制到 `review/` 目录归档，**不改写历史 review**；修复回应另存新文件（`revision-response.md`），差异存 `revision-diffs/`。

## 6. 禁止事项（再次强调）

- 不修改 `reference/` 任何文件；不切换/拉取/更新参考基线；不安装补丁或插件补足推测能力。
- 不创建 TS 包、MZ 插件、Showdown 适配器、战斗实现、引擎适配器或任何生产框架代码。
- 不运行游戏、Ruby、编译器、参考脚本、参考表达式、插件或网络请求；不操作真实地图/存档/输入。
- 不把"参考实现如何组织"当作"新框架应该如何组织"的依据；不复制源码、不逐行转写伪代码、不保留原类层次/方法结构/调用链作为规格。
- 不自行标记 Reviewed；不把自检当外审通过；不把搜索未命中当不存在；不把方法存在当实现；不把 return 值当业务成功；不单凭代码注释确认实际行为；不把材料缺口下的推测写成已确认事实。
- 不凭哈希前缀推补完整 SHA-256；不凭记忆填写字节数（一律 `shasum -a 256` 与 `stat -f "%z"` 实测）。
- 不替用户自动提交、推送或发布成果；不清理或覆盖用户已有工作；不自行创建并行 Agent。
