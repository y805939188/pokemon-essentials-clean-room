# 邮件与神秘礼物行为规格（净化正文；批次 9c）

分类：creature-rpg（主）＋ user-interface（画面）＋ generic-kernel（HTTP/文件载体接点）；性质：实现独立行为合同。

本规格为净化正文：按统一交接将批准输入 WP64《邮件与神秘礼物（保存/转移/候选/重复与领取）》转写为独立行为文字，不含源文件路径、类名、行号与证据 URL（参考与已读集中登记于 `../../audit/source-traceability.md` 批次 9c 条目）。文中保留的字段名、物品身份名与配置键均为数据标识，不构成未来实现的数据结构或接口模板。全部内容为静态证据；**无运行确认**（见 `../scope-statement.md`）。

---

## 1. 目的、边界与可见流程

### 1.1 目的与流程

邮件是附在个体上的可写消息物品：写信时把消息与三只成员快照封存进邮件对象，可随个体持有、被取下存入 PC 信箱、从信箱取回背包或再给予成员。神秘礼物是外部分发的领取凭证：作者侧用调试功能维护主文件并导出上传；玩家侧在载入画面下载候选、选择接收后由商店配送员交付宝可梦或物品。两套产物分开建模、互不复用状态：邮件没有下载/领取链，神秘礼物没有信箱与写信链。

### 1.2 范围

邮件数据与信箱（模型、快照次序、容量）；邮件流转（写信、阅读、取下、PC 信箱、给予链的部分提交事实）；神秘礼物的定义与载体（四元组、主文件/导出文件、加解密）；下载与候选（载入画面入口、去重、接收入队）；领取（配送员接口、宝可梦/物品写入序列、容量失败）；调试 authoring（编辑、创建、管理、导出）。

### 1.3 非目标

不定义物品使用与给予资格（WP28）、背包容器与容量（WP27）、收编与蛋入口规则（WP26，含已确认 GR-010，本规格只登记调用点）、图鉴登记规则（WP62）、HTTP 层实现（WP07，仅登记下载合同）、存档与载入画面本体（WP09）、队伍侧邮件命令与给予画面（WP66-A，其查明行为本规格已采用）、文本数据生命周期（WP04）。真实下载不执行（HTTP 仅登记合同与失败语义）、示例 URL 的可访问性不作结论前提、demo 配送员事件与解锁事件属 U01/WP77。

## 2. 邮件数据与信箱

### 2.1 邮件对象

字段：邮件物品（决定卡片图）、消息文本、发件人名、三只快照成员 poke1/poke2/poke3。快照在写信成功时从队伍现场截取，每项为 [物种， 性别， 闪光， 形态， Shadow, 蛋?]（蛋标记仅在是蛋时追加）：poke1 = 持有者在队伍中之后第二名成员（存在时）、poke2 = 之后第一名成员（存在时）、poke3 = 持有者本人（采用 WP66A-C02 纠正后的次序；WP66-A 已同步修订，两稿一致）。图鉴邮件（is_icon_mail?）在阅读时按快照绘出对应图标。

### 2.2 写信

给予邮件物品时触发（WP28 给予链）：自由文本输入（至多 250 字）；留空并确认「停止给予？」则放弃本次给予（返回 false）；写入成功才把邮件对象挂到成员（前提：成员当前无邮件，否则为防御性异常）。快照按 §2.1 截取。写信的取消路径不产生邮件对象，但不保证回滚调用链上已完成的其它写入（§3.3）。

### 2.3 信箱

全局信箱懒建立（初始 nil，首次存入时建为空表）；容量 10：存入已满时失败（调用方显示「PC's Mailbox is full.」）。信箱保存邮件对象本身（含消息与快照），不是邮件物品。

## 3. 邮件流转

### 3.1 阅读

队伍侧「邮件 → 阅读」与 PC 信箱「阅读」都打开同一阅读画面：卡片图、正文与发件人（按背景明暗配色）、图鉴邮件附加快照图标；USE/BACK 关闭，无任何写入（WP66-A 已登记画面行为，此处登记两处打开点）。

### 3.2 取下与 PC 信箱

- 队伍取下（WP66-A 邮件 → 取下/物品取下）：先过背包容量门（WP64-R01 查明）——背包不能再加入这件持物时直接提示背包满并结束（不询问存 PC、信箱与成员都不变）；通过后才询问「存到 PC？」——信箱未满则邮件入信箱、清空成员邮件与持物；信箱满失败保持原状；拒绝存 PC 再确认「消息将丢失」——邮件物品入背包、成员邮件与持物清空。存 PC 同样受背包容量门限制，信箱未满不能绕过。
- PC 信箱画面（PC「Mailbox」项）：空信箱只提示「There's no Mail here.」。对每封邮件的命令：

| 命令 | 门 | 写入 |
| --- | --- | --- |
| Read | 无 | 打开阅读画面（§3.1） |
| Move to Bag | 先确认「The message will be lost. Is that OK?」 | 邮件物品入背包（背包满则「The Bag is full.」失败保持原状）、信箱删除该封；消息与快照随邮件对象一并丢弃 |
| Give | 无 | 打开队伍给予画面（WP66-A）：成员已有持物或邮件 →「持物中不能持邮件」；蛋 →「蛋不能持邮件」；否则邮件写入成员、成员持物设为邮件物品、信箱删除该封 |

- 信箱进件唯一入口是队伍取下的「存到 PC？」分支；没有从背包直接入信的入口。

### 3.3 给予链的部分提交事实（WP66A-R01 查明行为；WP66-A 已同步修订，两稿一致）

邮件/持物给予链不是全有全无事务；取消写作时，调用链上已完成的写入不回滚：

1. 交换给予邮件：成员已持普通物品 X、背包有邮件 M。给予 M → 确认交换两件 → 背包先减 M、X 入背包 → 进入写信 → 留空并确认放弃。结果：给予返回 false，成员仍持 X，M 已回背包，而入包的 X 不回撤——背包 X 计数净 +1（防御异常仅在 M 无法回包时）。
2. 先取邮件再给予：成员原持邮件，给予新物品时链上先把原邮件成功存入 PC 信箱（成员邮件与持物清空）；随后新物品的写入（或新邮件的写作）被取消/失败时，先前的信箱入库与成员清空不回滚。

后续统一修订与本规格的流程描述均按此真实结果记录，不补造事务保证。

## 4. 神秘礼物：定义与载体

- 礼物为四元组 [id, type, item, giftname]：type == 0 为宝可梦（item 为宝可梦对象），type > 0 为物品数量（item 为物品 ID）；id 为整数标识（作者侧正常创建可提交的 ID 为 1–99,999 且与主文件查重——数字控件范围虽含 0，但 0 会进入「停止编辑」确认而不能提交（WP64-C01）；0 也是配送员接口「无待领取」的哨兵）。「唯一」只对作者新建成立：下载侧与领取队列不保证同 ID 唯一（WP64-R02，§5/§8）；giftname 为显示名（至多 250 字）。
- 载体：主文件 MysteryGiftMaster.txt（作者侧全量）与导出文件 MysteryGift.txt（选中在线项导出，用于上传）。编码为序列化 → 压缩 → base64；解密时物品条目经数据层归一化为内部 ID（宝可梦对象原样）。配置常量为下载地址（默认示例地址为占位；不以示例 URL 可访问性作为任何结论前提，WP07 的 HTTP 层另行负责）。
- 玩家侧持久：mystery_gifts（默认空表），元素为未领取礼物（四元组）或已领取标记 [id]；mystery_gift_unlocked（默认 false）控制载入画面入口（事件解锁，U01）。

## 5. 神秘礼物：下载与候选

- 入口：继续/新游戏载入画面在存档玩家 mystery_gift_unlocked 为真时提供「Mystery Gift」命令（WP09 画面侧），调用下载流程。
- 下载：WP07 合同分两段——运输层：HTTP 包装只对结构化（Hash）响应判断状态码（200 取 body、非 200 取空），下载调用范围内的普通异常与空结果按空串处理；非 Hash 响应原样透传。解码层（本规格）：空串提示「No new gifts are available.」并结束；但对非空载荷的解码没有本地异常兜底（WP64-R03 查明：base64/解压/反序列化错误或未知物品条目的错误会向外传播，不能统一归为空礼物；管理界面同样先解码再查空表，损坏编码不保证显示「无礼物」）。
- 候选：解码后按 ID 对既有队列过滤——玩家 mystery_gifts 中已存在同 ID（无论未领取还是已领取标记）的礼物不进入候选；候选为空同样提示无新礼物。去重仅限与既有队列比较（WP64-R02）：同一在线载荷内的重复 ID 不被排除（见 §8）。下载成功不等于领取：候选只进选择列表。
- 接收：逐件选择（可随时 Cancel）：宝可梦/物品图掉落动画、提示「The gift has been received!」与「Please pick up your gift from the deliveryman in any Poké Mart.」，随后推入玩家未领取队列（每次只删除所选候选，不重新按 ID 过滤剩余项）；候选耗尽自动结束。

## 6. 神秘礼物：领取

配送员事件接口（demo 事件属 U01）：「下一礼物 ID」查询返回队列中首个未领取礼物的 ID（无则 0）；「领取礼物（id）」执行领取。领取按 ID 逐项查找首个匹配的未领取项（WP64-R02）：队列中若存在同 ID 的多份未领取（来自同一载荷的重复 ID，§8），前一份被标记已领取不会阻止后一份匹配项再次被领取——不存在队列级唯一性校验。

### 6.1 宝可梦领取（type == 0）写入序列

1. 重摇 personalID（32 位随机）并重算能力。
2. timeReceived = 当前时间；obtain_method = 4（命运相遇）；record_first_moves；obtain_level = 当前等级；obtain_map = 当前地图 ID（无地图为 0）。
3. 记录此前是否已拥有该物种（was_owned）。
4. 静默赠送入口收编（WP26：队伍/盒子放置规则；失败则礼物保持未领取、返回 false，前述字段改写留在礼物对象上——该对象仍处未领取队列，其字段在下次领取时再次被改写）。
5. 成功：消息「X received Y!」＋音效；该礼物的队列元素改写为 [id]（已领取标记）。
6. 图鉴分支（默认配置 SHOW_NEW_SPECIES_POKEDEX_ENTRY_MORE_OFTEN 开，世代 ≥ 7）：此前未拥有、玩家有图鉴、该物种在已解锁图鉴内——提示数据已加入，登记最近见过（WP62），并打开图鉴条目画面。

### 6.2 物品领取（type > 0）写入序列

- 门：背包可添加预检（item, qty）；背包不能容纳（容量/上限）则失败，礼物保持未领取（WP27 规则）。
- 写入：按量入背包；消息按物品形态分流：DNASPLICERS 专属格式、机器（含数量与招式名）、数量 > 1 复数格式、单件按元音选择 a/an；随后队列元素改写为 [id]。

### 6.3 查找失败

按 ID 找不到未领取礼物时提示「Couldn't find an unclaimed Mystery Gift with ID X.」并 false（不改任何东西）。队列中的同 ID 多份各自独立（WP64-R02）；领取阶段的 ID 语义是队列内首个未领取匹配。

## 7. 调试 authoring（调试菜单）

- 编辑/创建：宝可梦礼物先选获得地短语（Mystery Gift/Faraway place/当前 obtain_text/自定义 30 字）；物品礼物改数量（1–99,999，取消为 0 视为放弃）；ID 为 0 时分配新 ID（与主文件现有 ID 查重，重复拒绝；可提交 ID 为 1–99,999，WP64-C01）；再命名（≤ 250 字）。各步留空/取消都会询问「Stop editing this gift?」，确认则放弃返回 nil；异常兜底「Couldn't edit the gift.」。创建把礼物追加到主文件（不存在则新建）并加密写盘；取消则「Didn't create a gift.」。从现有队伍成员创建宝可梦礼物时的别名写入（WP64-R05 查明）：调试菜单把原成员对象直接传入编辑流程，选择获得地短语时已原位改写该成员的 obtain_text；之后在 ID/命名阶段确认停止也不恢复——不创建礼物文件，但玩家现有成员状态已变。
- 管理：读取主文件（无文件或空 →「There are no Mystery Gifts defined.」；先解码再查空表——主文件存在但编码损坏时解码错误向外传播，不保证显示该提示，WP64-R03）＋联网下载在线列表（搜索提示；无在线礼物按空表）。列表逐项显示 [X]/[ ] 在线标记、ID、名称、内容；操作：Toggle on/offline（改在线标记集合）、Edit（§7 编辑）、Receive（有存档时把礼物替换/追加进玩家队列并立即按 §6 领取——无存档提示不能领取）、Delete（确认后从当前会话列表移除，不回写主文件）、Export selected to file（把在线标记的礼物导出 MysteryGift.txt 并提示上传）。四层状态分开（WP64-R04 查明）：Edit/Delete 不回写主文件；Edit 修改会话数据时，可能同时影响共享的玩家个体（见下），退出不回写主文件（退出重进仍读原文件）；Export 只写导出文件（按当前会话选中状态）；只有 Create 有主文件追加/写盘路径；线上内容只在人工上传后变化。

---

管理会话 Receive→Edit 的共享个体例外：合法主文件礼物 G（ID7、普通非蛋 PICHU P、获得地 Mystery Gift）、已加载玩家且队伍有位、无图鉴提示、在线列表为空、无插件或额外修改；同会话 Receive 成功加入的就是 P，玩家队列该项变 [7]，管理列表仍持有 P。随后 Edit G 先选 Faraway place，再在命名阶段留空并确认停止：编辑返回空、不替换管理条目、不写主文件，但已入队 P 的获得地已改为 Faraway place，取消不恢复。关闭管理重进只重新读主文件，不恢复队伍 P；未 Receive 且与玩家成员无共享关系的编辑对照不改队伍。

## 8. 规则与不变量

- 邮件与神秘礼物状态不交叉：信箱只存邮件对象；神秘礼物队列只存四元组与已领取标记。
- 邮件对象只在写信成功时创建一次；存信箱、信箱 Give、队伍取下都是转移同一个已有对象（WP64-C02），不再创建；阅读永不写入；取下两分支分别对应「转移入信箱保留」与「丢弃对象、物品回包」。
- 信箱容量 10 恒成立（存入方检查）；PC 信箱 Move to Bag 与队伍取下（含存 PC 意图）都受背包容量门（WP64-R01）。
- 神秘礼物的 ID 过滤只对既有队列（下载开始时的玩家队列，含已领取标记）；同一在线载荷内的重复 ID 不被排除、可逐项入队；领取按 ID 逐项查找首个未领取匹配（WP64-R02）。领取成功才改写为 [id]；领取失败保持未领取可重试。
- 给予邮件链的取消不产生邮件对象但也不回滚既有写入（§3.3 两条事实）。
- 调试 authoring 的落盘范围：Create 写主文件；Export 写导出文件；Edit/Delete 不落主文件，Edit 可改共享玩家个体（§7）；从现有成员创建时选择获得地即改写原成员 obtain_text，取消不恢复（WP64-R05）；线上内容不受任何调试操作直接影响。

## 9. 边界与失败

- 信箱满（10）：队伍取下存 PC 失败保持原状。
- 背包满：队伍取下先被容量门拦下（不询问存 PC，信箱未满也一样，WP64-R01）；PC 信箱 Move to Bag 失败保持原状；神秘礼物物品领取失败保持未领取。
- 收编失败（静默赠送 false，如队伍与盒子均无位）：宝可梦礼物保持未领取。
- 空信箱、无可下载（网络失败/空响应/全部已收）、候选选完、配送员按 ID 查无未领取：各有确定消息与返回。
- 邮件功能与 Pokégear 无关；神秘礼物入口只看解锁标志。
- 非空但无法解码的载荷（损坏编码、解压/反序列化错误、未知物品条目）：错误向外传播，不按「无礼物」处理（WP64-R03；运输失败与空内容才是空礼物分支）。
- 主文件缺失/为空（管理）：提示无已定义礼物；主文件存在但编码损坏：解码错误传播（WP64-R03）；编辑异常兜底消息。
- 同一在线载荷含重复 ID：候选不排除（只与既有队列比较），两份都可接收入队并可先后被领取（WP64-R02；作者侧新建时的查重另列）。
- 蛋：不能持邮件（给予链与信箱 Give 同门）。

## 10. 依赖与配置

- 规则引用：WP28（给予链与写信触发点）、WP27（背包可添加预检与上限）、WP26（静默赠送收编；GR-010 已确认、本规格只登记调用点）、WP62（图鉴登记与条目）、WP07（下载/HTTP 合同）、WP09（载入画面与存档）、WP66-A（队伍邮件命令与给予画面；WP66A-R01/C02 已采用）、WP04（文本与文件生命周期）、WP17（消息输入）。
- 配置：下载地址常量（占位示例地址）；SHOW_NEW_SPECIES_POKEDEX_ENTRY_MORE_OFTEN 默认开（世代 ≥ 7）；信箱容量 10；写信 250 字、获得地短语 30 字、命名 250 字、ID 1–99,999（0 不可提交且为无待领取哨兵，WP64-C01）、数量 1–99,999。
- 数据：物品数据含 12 个邮件物品（GRASSMAIL 等，is_mail?/is_icon_mail? 数据驱动）；主文件与导出文件为序列化+压缩+base64 载体。
