# TS／MZ／Showdown 宝可梦游戏开发框架：7 步简化计划

版本：v1.0 · 日期：2026-10-17

配套文档：[完整方案与实施计划](DETAILED-PLAN.md) · [规划说明与阶段对应](README.md)

## 1. 收尾整改，并行建立去向清单（当前正在做）

完成第八轮整改、独立复审和整体验收。同时建立覆盖全部规格章节的去向清单，统一分为框架、Showdown、双方协作、MZ 接入表现、不纳入目标五类；不纳入目标须由用户决策。暂缓单独登记为实现阶段，不与去向混为一类。清单可以先是临时版，随整改和原型回填；最晚在第 4 步开始前形成完整、可追溯的版本，技术未知项仍可明确标为待验证。

## 2. 验证战斗接入，确定路线和首版范围（可与第 1 步并行）

先固定最小实验基线：MZ、NW.js、Showdown 版本、Gen 8 配置和最小数据。在真实打包工程里验证战斗道具、捕获、逃跑、战中升级及数据写回。

结束时作一次明确决定：继续当前方案，还是调整。若扩展方案不可接受，向用户提交证据、成本和可选路线，由用户决定。结合结果确认首版范围，包括双打的交付阶段和长尾后置玩法，并重新估算工作量与排期。

## 3. 建立工程和测试基础

搭好 TS 项目、模块边界、内容数据格式、本地化、存档基础和自动化检查。建立第一批共用输入与预期结果的测试，跑通 Ruby 参考行为与 TS 实现的对照流程。

数据盘点、来源与许可清单、参考程序执行规则可在早期并行补齐；相关约定在实际使用前落实。

## 4. 做出最小可玩闭环

用占位素材和小地图跑通：获得精灵 → 遭遇 → 战斗／捕获 → 经验与升级 → 治疗 → 存档与读档。

验证模块之间的连接、取消和失败处理，测量性能基线。完成后再检查一次范围和排期，并制定性能预算。

## 5. 按功能族扩展

依照首版范围和依赖，逐步补齐队伍、仓库、背包、商店、图鉴、进化、孵化、地图能力、训练家 AI 等功能。

每个模块一起交付功能、测试、MZ 接口和示例。通过对照测试发现差异，就修正规格并加入回归测试；后置功能继续保留在清单中。

## 6. 完善作者工具和 Demo

补齐插件命令、内容校验、调试工具、自定义机制入口和使用文档。换入用户制作的 MZ 地图、人物与音画资源，完成使用同一套框架功能的示例游戏。

参考原版 Demo 的事件流程时，先提取行为规格，再据此重建。

## 7. 验收并发布

按已确认范围检查功能覆盖、Windows／macOS 运行、存档、性能和分发条件，发布首个可用版本及已知限制。

之后按计划继续补齐其余保留功能；暂缓、未验证和未实现的内容不算已覆盖。

整体节奏：整改与原型可并行 → 根据实验确定路线和首版范围 → 工程与测试基础 → 可玩闭环 → 扩展功能 → Demo 与工具 → 验收发布。
