# TS／MZ／Showdown 宝可梦游戏开发框架

完整方案与实施计划

版本：v1.0 · 日期：2026-10-17

配套文档：[7 步简化版](QUICK-PLAN.md) · [规划说明与阶段对应](README.md)

## 一、项目目标

从零使用 TypeScript 实现一个直接用于 RPG Maker MZ 的宝可梦游戏开发框架。

游戏作者能够通过 MZ 地图编辑、事件命令、内容配置和扩展代码制作游戏。框架负责养成、队伍、仓库、背包、经济、遭遇、世界流程、界面和存档；Showdown 负责战斗模拟，通过受控扩展支持单机 RPG 行为。

最终交付：

- MZ 插件、运行数据和安装入口。
- 类型化开发 API、编辑器侧事件命令。
- 内容校验、编译、调试和发布工具。
- 自动化测试、参考行为证据与覆盖清单。
- 可玩的 MZ demo、作者文档和扩展示例。

目标是行为可验证、职责清晰、易维护、方便 AI 理解，并通过测量约束性能。

## 二、范围与完成口径

所有参考功能都有明确去向，分为五类：框架、Showdown、双方协作、MZ 接入表现（按 MZ 方式重建）、不纳入目标。不纳入目标须由用户决策；暂缓单独记录为实现阶段，不与去向混为一类。

保留功能通过验收后才算覆盖；有意变化记录理由和差异；暂缓、未实现、未验证不计入完成。

区分三个交付层级：

### 1. 技术原型

验证运行环境、扩展机制和状态同步，不代表完整游戏功能。

### 2. 首个可用版本

建议包含精灵实例、队伍、仓库、背包、商店、基础图鉴、成长、遭遇、训练家、单打、基础 AI，以及捕获、逃跑、战斗道具、学招、进化、菜单和存读档闭环。

双打在早期原型中验证，正式交付阶段在产品范围表中明确。

### 3. 完整覆盖版本

逐批完成全部决定保留的功能，包括培育、完整 AI、野外能力、特殊玩法、更多战斗模式和长尾行为。

联网、浏览器／移动端发布、完整录像播放器等能力单独排期。首版范围和暂缓列表纳入完整基线，并结合高风险原型结束时的决策确认，至少明确双打的交付阶段和长尾后置项，重新估算工作量与排期；不把建议当作已经批准的功能删减。

## 三、第八轮整改收口

本轮退出条件：

- 29 项必改完成修订、独立复审和整合验收。
- 10 项可选明确选入或保留。
- 必要依赖闭合，未满足依赖的问题保持开放。
- 固定规格版本、参考版本、问题状态及已知限制。

整改验收后冻结第一版正式实现依据，不再默认开展新的全局静态规格 review。

实现阶段继续进行模块测试、代码审查和发布验收。新问题以实际证据驱动定向修正。

隔离技术原型可以与整改并行。原型若使用仍在修订的契约，结果标为临时，正式基线确定后复验。

## 四、基线分两层建立

### A. 原型启动所需的最小基线

先确定：

- 本次实验的目标平台与 CPU 架构。
- 实际 MZ、NW.js、内嵌 Node 和 Chromium 版本。
- Showdown 完整提交 SHA、构建方式与依赖锁文件。
- Gen 8 实验配置及必要规则参数。
- 最小精灵、招式、道具数据与实验场景。
- 稳定 ID 规则、最小内容 schema、异步消息初版。
- 实验实际使用代码、数据和资源的来源与使用条件。

这些条件满足即可开始原型，不等待全部治理材料完成。

### B. 与原型和工程基础并行补齐的完整基线

包括：首版范围、章节级覆盖清单、完整来源与分发清单、本地化约定、内容规范、参考观察流程和 demo 参考资料盘点。

章节级粗标与整改并行，初版可为临时版，随整改和原型回填。各项在相关工作开始前具备必要约定，最晚在阶段 3 可玩闭环开始前形成完整、可追溯的基线；技术未知项允许明确标为待验证。正式规格冻结仍以第八轮整改验收为前提。

具体 MZ／NW.js 版本需实测填写；不能用开发机的 Node 版本代替 NW.js 内嵌版本。

## 五、产品与规则配置

建议桌面离线优先，面向 Windows 与 macOS，分别验证最终打包结果。键盘与鼠标为基础输入，中文为首版主要内容语言。

首版默认规则目标为 Gen 8，具体变体通过参考配置与数据盘点确定。其他世代进入后续支持清单。

统一配置入口分别管理：

- 战斗世代与变体。
- 物种、招式、特性、道具的可用范围。
- 非战斗规则参数。
- 特殊模式和游戏自定义覆盖。

默认规则保持协调，允许明确声明、经过校验和测试的覆盖。世代编号不自动决定竞技限制或全部内容范围。

## 六、实现覆盖清单

先做章节级全覆盖，模块开工时细化为行为单元。章节级粗标与整改并行，初版可临时，最终随整改和原型回填；最晚在阶段 3 可玩闭环开始前形成完整、可追溯的版本，技术未知项仍可明确标为待验证。去向、依赖、验证方法或验收状态不同的内容分别登记。

去向统一为框架、Showdown、双方协作、MZ 接入表现、不纳入目标五类；不纳入目标须由用户决策。暂缓属于实现阶段，单独登记，不改变去向分类。

每行包含：

- 稳定功能 ID、行为描述。
- 来源规格的冻结提交、文件与章节锚点。
- 当前适用版本及定位。
- 去向、目标版本、实现阶段（含暂缓）、责任模块和依赖。
- 验证状态、实施状态、证据位置。
- 已知差异、问题和决策。

验证状态与实施状态分开：原型验证成功不等于实现完成，实现完成不等于整合验收通过。

规格勘误时保留原冻结定位，更新当前定位；稳定 ID 不随章节重排变化。功能变更同步更新对应清单行。

## 七、架构与依赖方向

同一仓库内按职责划分六类模块：

### 1. 内容数据

定义、校验和编译物种、招式、特性、道具、训练家、遭遇、文本和资源索引。

### 2. 游戏规则

实现精灵实例、队伍、仓库、成长、培育、进化条件、背包、经济和图鉴等，可脱离 MZ 画面测试。

### 3. 游戏流程

组织开战、结算、捕获入队、学招、进化等多步骤流程，协调规则、界面与持久状态。

### 4. 战斗接入

集中负责 Showdown 转换、RPG 扩展、消息协议、AI 快照、结果同步和版本适配。

### 5. MZ 接入与呈现

负责地图、事件解释器、场景、窗口、输入、音频、资源加载和存读档入口。

### 6. 工具与测试

提供构建发布、内容错误定位、调试菜单、差分测试、契约测试和覆盖报告。

依赖方向由工具约束：规则模块不直接引用 MZ 全局对象或 Showdown 内部类型；游戏流程通过明确接口使用宿主能力；接入模块实现这些接口。

采用严格 TS、导入边界检查、循环依赖检查和无宿主测试。初期保持模块目录清晰，不急于拆成大量独立发布包。

每个模块提供简短说明：职责、公共入口、状态归属、输入输出、关键示例和测试命令，便于人和 AI 定位工作范围。

## 八、战斗协议与状态同步

从原型开始采用异步命令、事件和只读快照，消息可序列化。业务模块不持有战斗引擎内部对象。

初版只定义实验必需的内容：会话身份、请求关联、事件顺序、错误和结束语义。状态版本、取消、重复请求等随原型完善。

阶段 1 结束时，根据证据冻结第一版战斗协议、状态归属与同步点。

状态原则：

- 战斗会话掌管战斗内状态。
- 持久状态在明确同步点更新。
- UI 提交操作并展示结果，不直接改队伍或背包。
- 道具消耗、奖励等提交可追踪，并防止重复执行。
- MZ 事件具有明确的等待、取消、失败和恢复结果。

初期可以同进程执行。是否迁移到 Worker 或子进程由实测决定；异步接口降低迁移成本，但不自动消除主线程计算阻塞。

## 九、Showdown 构建与 RPG 扩展

固定上游源码与独立补丁集，在受控构建环境中生成模拟器产物。MZ 发布包加载经过验证的编译结果、数据与必要依赖。

构建记录保存上游 SHA、补丁、工具版本、命令和产物身份。升级上游时重跑受影响契约测试。

优先验证适用的 mod／规则扩展点，不足时维护最小受控补丁。所有内部耦合集中在战斗接入模块。

重点验证：

- 带已有 HP、PP、状态和持有物进入战斗。
- 单打、双打、强制换人和精灵身份映射。
- 战斗内背包道具、投球和逃跑。
- 战中经验、升级、能力值变化和学招。
- 战斗后的准确写回。
- 异常、中断、重复请求与必要的日志重放。

选型标准：

- 时序正确，包括行动排序、换人、失败与回合末效果。
- 状态正确，战斗与持久数据一致。
- 不产生不适用的招式、特性或记录副作用。
- 能无界面测试，并在真实 MZ 打包环境复验。
- 补丁范围、升级成本和责任清楚。
- 输入、事件和错误能够诊断。

先满足正确性，再比较维护和性能成本。占位招式或外围结算可以实验，但正式采用必须证明目标语义成立。

原型失败时先定位环境、扩展点或契约问题，再评估 Showdown 路线内的调整。仍不可接受时，向用户提交证据、成本和范围选项，由用户决定，不自动删功能或改换战斗方向。

## 十、AI 与自定义战斗内容

AI 通过适配器取得只读战场快照，并经过信息权限过滤。评分后返回候选行动，由接入模块校验合法性。

隐藏招式、道具、特性和历史观察的使用范围明确规定。基础可玩 AI 与完整参考行为保真分别验收。

作者内容分三级：

- 数据配置：修改允许字段，选择已注册效果模板与参数。
- 模板继承：从既有条目派生并按规则覆盖。
- TS 扩展：注册全新效果及测试。

数据仅引用效果 ID，不嵌入可执行代码。内容模块开工前明确字段、参数 schema、继承循环、冲突与错误处理。模板支持范围按版本交付。

## 十一、作者数据与本地化

建议 JSON＋schema 为默认作者格式，编译为统一运行时数据。PBS 提供指定范围的导入能力，并输出未支持字段、信息损失和待人工处理项。

稳定 ID 与最小 schema 在原型前确定；各模块的完整 schema 在其开工前冻结，后续变更有版本与迁移办法。

校验覆盖 ID、引用、形态、数值范围、资源存在性与战斗映射。Showdown 数据、框架数据和游戏自定义覆盖各有明确归属。

自动数据盘点比较物种、招式、特性、道具及相关配置，区分一致、有差异、单侧存在、无法直接比较。字段对比和行为核对分别输出，数据一致不计作行为覆盖。

本地化设计：

- 实体 ID、文本 key 与显示名称分离。
- 名称、UI 和事件对话使用统一解析入口。
- 支持参数替换、回退语言、缺失 key 检查与字体映射。
- 使用第二语言小样测试切换、长度和布局。
- 完整多语言内容量单独安排。

## 十二、Ruby 参考观察与测试

执行原版前形成流程决策记录：参考版本、执行角色、环境、允许输出、检查方式和证据位置。

参考观察端读取和运行原版，控制输入并提取行为；实现端接收规格、数值、状态和事件序列。材料不夹带 Ruby 实现代码或实现片段。

历史“参考执行为 0”的记录保持原样，新执行证据按版本与时间独立登记。

文字场景按模块转换为机器可读用例，保留场景 ID，包含初始状态、操作序列、配置、时间／随机条件、输出、状态变化、事件与失败结果。

证据区分静态推导、原版运行、替身环境运行和人工确认。

测试层次：

- 纯逻辑单元测试与 Ruby 差分。
- 受控服务替身测试。
- 兼容运行时和实际工程集成测试。
- Showdown 契约测试与 MZ 端到端测试。
- 视觉、音效和操作体验的自动检查与人工验收。

随机验证使用精确边界、受控随机决策、不变量和统计检验。统计检验预先确定样本和容差；相同 seed 不作为跨语言轨迹一致的证明。

差异先分类为规格错误、实现错误、环境差异或有意改变，再修改对应内容。

## 十三、存档、恢复与 demo

普通存档保存框架定义的版本化数据，接入 MZ 存档入口，提供校验、迁移和失败处理。

建议首版在战斗外保存。战中续玩若纳入范围，单独验证引擎快照、会话、道具消耗与奖励提交的一致性，并绑定引擎、规则、补丁和内容版本。

完整录像播放器单独验收输入日志、随机状态、扩展行动、资源版本和呈现流程。

demo 从可玩闭环开始：

- 初期使用占位地图、合法占位资源和基础界面。
- 后期替换为用户制作的 MZ 地图、角色、音乐与正式表现。
- 始终使用同一套业务代码。

参考端先盘点完整发行包的地图、公共事件、配置和资源依赖，再提取触发条件、流程、状态变化和预期结果。实现侧据此重建 MZ 示例。

素材重制与事件实现分别推进，缺失资料明确登记。

## 十四、来源、许可与发布

实际使用代码、数据和素材前，核对其来源与使用条件；完整分发清单并行建立，在相关交付前确认。

框架源码包、插件包、demo 分别明确包含哪些文件及必要的许可、署名和分发要求。

Windows 与 macOS 分别测试。macOS 的开发可运行与正式分发分开验收，签名、公证、安装和首次启动体验列入发布条件，并记录账号、证书和构建环境等前置资源。

## 十五、变更流程与性能

问题闭环：发现问题 → 最小证据 → 分类 → 修改代码／规格 → 回归测试 → 更新覆盖行 → 分级验收。

- 低风险文字澄清：作者自检和自动检查。
- 边界明确的局部修正：相关回归与轻量验收。
- 职责、时序、存档、兼容范围或跨模块语义变化：决策记录和独立复审。

正文保持最终规范，勘误历史单独维护。

从第一条可玩闭环开始，在固定设备、运行时、规模和场景下测量：冷启动、地图切换、首次战斗、决策 p50／p95、长帧比例、存读档、满仓库及连续运行内存变化。

可靠基线形成后确定预算和回归阈值。初期 CI 警告，指标稳定后设置阻断门槛；画面性能仍在目标设备验证。

## 十六、实施阶段与验收

### 阶段 0A：最小基线

完成实验所需的版本、运行时、Gen 8 配置、最小数据、ID／schema 和使用条件核对。

验收：输入可追溯，实验可以重复启动。

### 阶段 0B：完整基线与整改

并行完成第八轮整改、范围表、覆盖清单、本地化、参考观察约定和分发资料。章节粗标可先临时，随整改和原型回填；技术未知项明确标为待验证。

验收：相关模块开工前具备必要约定，阶段 3 可玩闭环开始前形成完整、可追溯的基线，正式规格经过整改验收。

### 阶段 1：高风险原型

满足阶段 0A 最小基线即可启动，可与阶段 0B 的整改及完整基线工作并行。

顺序：运行时与加载 → 最小道具行动 → 投球／逃跑／战中成长 → 状态同步和消息协议。

退出清单：

- 打包后的游戏在目标 NW.js 中运行战斗。
- 道具、投球、逃跑、战中升级各有可重复成功场景和代表性失败／受限场景。
- 行动顺序与副作用符合目标契约。
- 写回数据符合实际战斗变化，未受影响的数据保持不变。
- 重复请求／结算不会重复扣道具或发奖励。
- 协议经过排序、错误、取消或结束流程验证。
- 双打至少通过一个关键组合场景。
- 形成扩展选型决定，并冻结第一版协议、状态归属与同步点。

检查点：原型结束时明确决定继续当前方案还是调整。若扩展方案仍不可接受，向用户提交证据、成本和可选路线，由用户决定。结合结果确认首版范围，至少明确双打交付阶段、长尾后置项，并重新估算后续工作量、风险与排期。

### 阶段 2：工程基础与首条差分链

交付构建、持续集成、依赖约束、内容编译、本地化、存档基础、日志，以及一个模块的 Ruby／TS 对照。

验收：能够重复构建、执行测试、定位差异并追溯证据。

### 阶段 3：最小可玩闭环

完成领取精灵、遭遇、战斗、捕获／奖励、成长、回血、存档恢复。

交付真实 MZ 占位 demo、异常路径测试和首份性能基线。

验收：闭环反复运行，取消、失败和重复触发不损坏状态。

检查点：重新估算首版剩余工作并确定性能预算。

### 阶段 4：分批完善功能

按依赖推进精灵与存储、背包经济、图鉴、成长培育、世界遭遇、训练家 AI、战斗变体及其余保留玩法。

每批同时交付规则、接口、界面、事件入口、测试、文档及 demo 示例。

验收：批次证据齐全、必要依赖闭合，并通过整合测试。

### 阶段 5：作者体验与正式 demo

完善内容模板、TS 扩展示例、调试工具、错误定位、事件配方、正式素材和文档。

验收：干净 MZ 工程能够按文档安装，并完成常见自定义内容与游戏流程。

### 阶段 6：发布验收

核对本版本功能清单、已知差异、打包运行、存档迁移、性能和分发条件。

交付固定发布包、安装文档、测试报告和版本范围说明。

后续版本沿用阶段 4 至 6，直到全部保留范围验收完成。

## 十七、日常推进方式

维护短任务看板，每项一行记录：目标、固定输入、依赖、产物／验收证据、状态。

任务内部明确可修改范围、接口、用例和完成条件。数据盘点、参考观察和不冲突模块可并行；共享接口按“实验初版 → 验证 → 冻结”的顺序协调。

模块通过与端到端通过分别登记。日常进展更新看板，只有范围、选型、接口等重大决策改变时更新方案。

最近的起步顺序：

1. 核对最小运行基线，验证打包 MZ 加载 Showdown。
2. 在隔离原型中验证最小道具行动的排序与副作用。
3. 固定输入后并行开展数据盘点和参考观察流程准备。
4. 扩展原型到捕获、逃跑、战中成长与状态同步。
5. 根据实测结果确定扩展方式、协议和后续排期。

这份计划作为后续任务拆分依据；具体版本、首版范围和待验证决策在对应阶段落实。
