# 战后提交、回程与存档

**独立实现规则 · V1-03**　WP09／WP10／WP11／WP42／WP61

[载入](../core/save-startup-continue.md)、[恢复](../core/migration-failure-recovery.md)、[传送](map-topology-transfer.md)及[败北回程](field-passive-effects-and-blackout.md)保留原版入口、异常前缀及未验证条件。不要将原版事件通知、备份或地图恢复次序替换为新宿主次序。

改良分三层：

1. **业务提交**：同一战斗的同一结果只结算一次；同一战斗标识却给出不同结果不得覆写。提交前已确认取消不产生部分业务写入。主体一旦已提交，呈现故障不撤销它；不能确定是否提交时先查证，不盲目重做。读档／新游戏替换状态后，旧会话迟到的结果或取消都不能改写新状态或释放新操作。
2. **回程完成**：已请求传送与玩家确实落位、后续事件能够正常运行是两件事。测试应观察目标地图、位置与发起旧事件的收尾，不以传送请求、场景载入或返回值代签。
3. **持久化**：若宿主原本请求自动保存，却因受控回程仍在进行而暂缓，只在同一回程到达且旧事件已退场后重新交付一次，交付时重新检查用户开关和保存资格。没有原请求就不补写；取消或状态替换让旧请求失效。保存通过需要真实写入与独立冷读；自动目的与手动目的分别测，不规定物理槽编号、帧数或文件格式。

这一独立实现曾在早期实机测试中失败；后续结论仅覆盖该实现的受控测试。玩家发布包、其他平台与原版游戏均须分别验证。

静态验收用例见[可移植向量](../../vectors/portable.json)。对应编号为 V1-03-A, V1-03-B, V1-03-C, V1-03-D, V1-03-E。
