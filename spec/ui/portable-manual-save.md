# 暂停菜单的手动存档确认

**独立框架行为。** 以下描述暂停菜单采用的手动存档流程。参考版本的保存摘要、确认和退出前保存见[原版主导航](title-load-options-pause-and-pc.md)。保存主体与载入规则见[保存与继续](../core/save-startup-continue.md)，受控回程的自动保存见[战后回程与存档](../world/portable-defeat-return-and-saving.md)。

## 入口与选择槽位

在提供存档场景、暂停菜单和命令窗口的宿主中，从暂停菜单的保存项进入手动槽列表。该框架沿用宿主菜单的可用性规则；已列出但禁用的保存项不能开始写档。此确认仅随暂停入口安装。测试宿主为自动存档保留槽 0，普通手动选择不能写入该槽；其他手动槽按宿主列表提供。

仅当前活动且尚未切换的保存画面能接受选择。已有待确认请求或正在写入时，重复选槽没有新动作。游戏与目标槽均允许保存才可打开确认。这个动作记录槽号、当时的游戏会话及槽文件是否存在，暂停列表输入；它不更改游戏的保存槽号，不执行保存前处理，也不写数据。

## 确认与取消

| 打开确认时的条件 | 显示与结果 |
| --- | --- |
| 槽文件不存在 | 询问是否保存到所选槽号。标题预览索引即使有旧行，也不构成文件已存在的证据。 |
| 槽文件存在 | 询问是否覆盖所选槽号。缺少索引行、缺少可读预览或文件含既有字节，均不能把实际存在的文件当作空槽。此检查只判存在，不先解析旧文件。 |
| 初次询问或再次询问覆盖 | 两项次序为“是、否”，默认焦点在“否”。中文与英文提示均显示所选槽号；选择提示和失败提示随界面语言切换。 |
| 选择“否”或按返回 | 清除待确认请求，关闭确认框并恢复同一槽的列表及选择提示。旧文件、游戏的保存槽号和保存计数保持。确认框与列表都要求新的确认或返回按键沿；持续按住不会跨过两层再打开或退出。列表收到下一次新的返回动作才回到暂停菜单。 |

## 确认时的复查与竞争

选择“是”先核对画面仍是当前画面、没有切换；失效画面的回调不执行。有效确认先消费该请求，再核对仍是同一游戏会话、保存仍开启且**原请求的槽号**仍可写。任一后置条件失败，显示保存失败并返回列表，到此没有调用写档。

最初为空的目标在这次复查时已有文件，会重新显示覆盖询问，仍默认“否”，尚未写入；必须再明确选择“是”。最初已占用的目标只记录“存在”这一状态。确认期间他人替换其内容，不会因为字节改变再询问；若文件已经移走，也不会再询问一个空槽。许可通过后交给原请求的槽号。同一画面的重复提交受抑制；存在性复查与后续存储不是跨进程锁或带版本条件的事务，复查之后外部写入的先后及最终内容没有统一保证。

## 写入、失败与继续

1. 请求进入写入状态后交给宿主手动保存，槽列表和确认框都不接受第二次写入。生产框架先检查已载入状态可用、内容与布局有效，且没有阻止保存的读取、迁移预览、战斗或其他框架操作。构造实际保存内容时再检查快照。任一框架数据检查拒绝都不写目标槽；不会借由手动确认修复无效资料。
2. 槽内进度主体与标题预览索引是不同的写入。正常的合成例先写槽主体，再发起全局索引写入，当前画面按宿主成功结果回到暂停菜单。保存成功回调没有等待标题索引持久化；立即退出进程时索引是否写完，以及部分写入后的磁盘状态均须另验。不能用界面已返回或只有索引行证明冷读成功。
3. 执行保存同步抛出或宿主报告失败时，仍处于当前画面的请求解除写入状态，显示失败并在原槽行接受重试。重试重新判断槽文件是否存在并要求确认。迟到的成败回调不导航新画面；已交给存储的操作不因画面切换而获撤销保证。
4. 标题索引已经就绪且该槽主体可读取时，在只共享已保存数据的新宿主中选“继续”，进入槽列表，选择目标槽，读回该槽，成功后进入地图并执行载入后的处理。判定读回结果应核对实际进度，例如金钱和队伍。暂停确认不会把自动保存、其他直接保存入口或继续读档改为同一个确认流程。

[手动存档验收向量](../../vectors/portable-framework-cases.json)包含普通保存、拒绝、空槽转占用、失败重试和冷读对照。向量为静态预期。既有宿主用例采用两套受控环境与合成内存存储，未验证真实玩家档、物理按键、文件压缩、进程骤停或跨进程覆盖的结果。
