1	# Pokémon Essentials Clean-Room Specification Project
2	
3	## Mission
4	
5	This workspace exists only to study Pokémon Essentials as a reference implementation and extract:
6	
7	* observable behavior
8	* game rules
9	* functional requirements
10	* domain concepts
11	* state transitions
12	* mathematical rules
13	* input/output behavior
14	* edge cases
15	* user-facing workflows
16	* feature dependencies
17	* compatibility requirements
18	
19	The final purpose is to support a later independent clean-room implementation.
20	
21	This workspace MUST NOT implement the new framework.
22	
23	---
24	
25	# Core Principle
26	
27	Pokémon Essentials is a behavioral reference, NOT an architectural template and NOT a source-code template.
28	
29	The goal is to answer:
30	
31	> What behavior and capability does the system provide?
32	
33	Do NOT answer:
34	
35	> How should we translate the existing Ruby implementation into TypeScript?
36	
37	---
38	
39	# Strict Source Separation Rules
40	
41	The directory:
42	
43	`reference/pokemon-essentials/`
44	
45	contains reference source material.
46	
47	It is READ-ONLY for this project.
48	
49	Never:
50	
51	* modify files under `reference/`
52	* generate patches for Pokémon Essentials
53	* refactor Pokémon Essentials
54	* translate Ruby code into another language
55	* output copied source-code fragments into specifications
56	* reproduce substantial source expressions
57	* preserve source-specific implementation structure unless necessary for analysis
58	* propose a TypeScript class hierarchy based directly on the Ruby class hierarchy
59	
60	---
61	
62	# Clean-Room Output Rules
63	
64	Specifications must describe behavior independently of source implementation.
65	
66	Allowed outputs include:
67	
68	* functional requirements
69	* domain concepts
70	* rules
71	* algorithms expressed mathematically or behaviorally
72	* state machines
73	* inputs and outputs
74	* preconditions and postconditions
75	* edge cases
76	* invariants
77	* examples
78	* test vectors
79	* user-visible behavior
80	* feature dependencies
81	* compatibility requirements
82	* implementation-independent pseudocode only when absolutely necessary
83	
84	Prefer prose, tables, diagrams, state machines, equations and test cases.
85	
86	Do not reproduce source code.
87	
88	Do not convert Ruby syntax into pseudocode line-by-line.
89	
90	Do not preserve method structure merely because the original implementation used it.
91	
92	---

112	# Classification Model
113	
114	Every discovered feature should be classified into one of these conceptual groups when possible:
115	
116	## Generic Kernel
117	
118	Capabilities useful to many kinds of games, such as:
119	
120	* persistence
121	* random-number services
122	* events
123	* configuration
124	* resource identifiers
125	* registries
126	* plugin/extensibility mechanisms
127	
128	## Creature-RPG
129	
130	Generic monster/creature collection RPG capabilities, such as:
131	
132	* creatures
133	* species
134	* parties
135	* inventory
136	* storage
137	* encounters
138	* progression
139	* evolution
140	* breeding
141	* capture
142	* player/trainer concepts
143	
144	These specifications should avoid Pokémon-specific assumptions where possible.
145	
146	## Pokémon Rules
147	
148	Pokémon-specific mechanics such as:
149	
150	* Pokémon stats
151	* IVs
152	* EVs
153	* Nature
154	* Types
155	* Pokémon-specific evolution conditions
156	* Pokédex behavior
157	* Poké Balls
158	* Pokémon-specific capture mechanics
159	* Pokémon-specific progression rules
160	
161	## Combat Requirements
162	
163	Requirements that the future combat subsystem must satisfy.
164	
165	Do not prescribe the combat implementation.
166	
167	## Engine / Overworld Integration
168	
169	Behavior currently connected to RPG Maker XP or RGSS, such as:
170	
171	* maps
172	* events
173	* player movement
174	* terrain interaction
175	* scenes
176	* graphics
177	* audio
178	* input
179	* save integration
180	
181	Describe required behavior, not the RMXP implementation.
182	
183	## User Interface
184	
185	Observable UX and interaction requirements.
186	
187	## Demo / Developer Experience
188	
189	Capabilities demonstrated by the bundled example project and workflows needed by future game developers.
190

253	# Completeness Discipline
254	
255	When analyzing a domain:
256	
257	* search for all relevant files
258	* inspect callers and dependencies when necessary
259	* look for configuration and data definitions
260	* inspect related demo usage
261	* check edge-case handling
262	* update the global Feature Matrix

265	Never infer that a feature does not exist simply because it was not found in the first file inspected.
