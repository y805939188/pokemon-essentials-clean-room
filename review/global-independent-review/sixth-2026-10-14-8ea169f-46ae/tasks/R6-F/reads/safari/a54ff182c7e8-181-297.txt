193: # Feature Documentation Standard
194:

196: 
197: 1. Purpose
198: 2. User-visible behavior
199: 3. Domain concepts
200: 4. Inputs
201: 5. Outputs
202: 6. Preconditions
203: 7. State changes
204: 8. Rules and invariants
205: 9. Edge cases
206: 10. Failure behavior
207: 11. Dependencies on other features
208: 12. Configuration/data requirements
209: 13. Example scenarios
210: 14. Test cases or test vectors
211: 15. Classification
212: 16. Open questions
213: 17. Source traceability

217: # Source Traceability
218: 
219: For each specification, record which reference files or demo behavior were inspected.
220: 
221: Traceability is for audit purposes only.
222: 
223: Do NOT reproduce source code in the specification.
224: 
225: Use paths and concise descriptions, for example:
226: 
227: * `Data/Scripts/...`
228: * inspected demo event behavior
229: * observed runtime behavior

233: # Workflow
234: 
235: Always work incrementally.
236: 
237: The required order is:
238: 
239: 1. Repository reconnaissance
240: 2. High-level module inventory
241: 3. Feature inventory
242: 4. Dependency mapping
243: 5. Specification extraction plan
244: 6. Detailed module-by-module extraction
245: 7. Cross-module consistency review
246: 8. Coverage review
247: 9. Final sanitized specification set
248: 
249: Do not attempt to fully document the repository in a single pass.
250: 
251: ---
252: 
253: # Completeness Discipline
254: 
255: When analyzing a domain:
256: 
257: * search for all relevant files
258: * inspect callers and dependencies when necessary
259: * look for configuration and data definitions
260: * inspect related demo usage
261: * check edge-case handling
262: * update the global Feature Matrix
263: * explicitly record uncertainty
264: 
265: Never infer that a feature does not exist simply because it was not found in the first file inspected.
266:
