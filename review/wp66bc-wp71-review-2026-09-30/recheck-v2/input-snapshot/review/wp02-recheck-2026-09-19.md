## 3. F1：附表生成的“值”不可靠，且一行表格结构被破坏

归属：延续 WP02-R01 的完整性与一致性验收，非重新打开全部六项。

定位：
- `specs/kernel/wp02-settings-inventory-appendix.md@6fba2cdd`：143、146、166–170 行。
- `analysis/inventory/wp02_build_appendix.py@898134d0`：51–72、85、154–155 行。
- `analysis/inventory/wp02_settings_inventory.py@46f1ba84`：30–42 行。

### 已复现的具体问题

| 条目 | 当前附表输出 | 固定基线可确认的值 |
|---|---|---|
| APPLY_HAPPINESS_SOFT_CAP | 默认值列为 `AFFECTION_EFFECTS` | 默认声明跟随 false，故默认值为 false；引用关系应留在派生列 |
| SCALED_EXP_FORMULA | 默认值列为“未求值”，附带原表达式 | 世代 8 下为 true |
| Essentials::VERSION | 值列为“独立” | `21.1` |
| Essentials::ERROR_TEXT | 值列为“独立” | 空字符串 |
| Essentials::MKXPZ_VERSION | 值列为“独立” | `2.4.2/c9378cf` |

“未求值”本身是诚实的求值器限制，不应指控为伪造；但它意味着不能把该附表说成默认值已经全部算出。主文档和 S1 已给出 true，需把表达式、结果与解析限制分列或协调清楚。

根因：
1. build_appendix 的 rec 顺序是 file/line/key/classification/value/group；元信息渲染使用了 m[3]，拿到的是 classification，而不是 m[4] 的 value。这个错误会在重新生成时再次出现。
2. 两个 eval_gen8 都没有处理 Ruby 的 `||`；受控输入复现返回“未求值”。
3. 设置间引用没有在求值阶段解析，所以默认值列保留引用名。
4. 未求值表达式包含未转义的 `||`，使附表第 146 行出现 7 个单元格，而表头定义 5 个。Markdown 单元格中的竖线必须转义或用不产生分隔符的表达。

### 最小修复要求

- 修正元信息列索引。
- 对该固定基线所需的有限表达式求值，或用显式、可追踪的人工确认结果填补未求值项。无需实现通用 Ruby 解释器。
- 明确区分“派生/表达式”“当前默认值”“未求值及原因”。不要把说明和真实值放进同一个语义不明的字段。
- 修复 Markdown 单元格转义。
- 同步实际生效的生成路径；不能只改最终 Markdown 而让脚本下次又生成旧错误。
- 附表第 4 行/manifest 应准确描述数据与渲染来源：当前实际 Markdown 是 build_appendix.py 写出，另一个脚本是独立的控制台清单程序；不能让读者误以为后者直接生成该 Markdown。

### 有界验收

1. 上表五个值与定义/主文档一致。
2. 所有常量表行均为 5 列；无裸竖线破坏结构。
3. 逐定义集合保持完整，不能通过删掉困难条目达到通过。
4. 在隔离输出目录重新生成一次，与提交附表比对；参考文件前后不变。
5. 保留生成命令、输入基线/哈希和输出哈希。遇到未求值必须显式报告，不静默吞掉。
