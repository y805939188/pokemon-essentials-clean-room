# 后续行为规格提取计划

本轮只制定计划，**不执行下列任何详细提取包**。输入基线为 [repository-overview](../analysis/repository-overview.md)，领域为 [module-map](module-map.md)，覆盖单位为 [feature-matrix](feature-matrix.md) 的 113 个高层组。（初始阶段说明：本节与文末的阶段表述描述计划制定时点；当前执行进度以各工作包登记、Feature Matrix 条目状态与 `planning/review-manifest-2026-09-19.md` 为准——2026-09-19 起 WP01 范围与 WP02 范围已先后交付送审。）

计划包含 **87 个可执行 Work Packages**，覆盖 18 个领域。其中 WP47、WP52、WP66、WP67、WP73 仅是任务族简称，实际分别执行其 A/B 或 A/B/C 子包，简称不另计任务。ID 用于追踪主题，不是目录顺序或必须连续执行的序号。

**当前推进优先级（用户指令，2026-10-01）**：先完成剩余内容包的提取与自检，再做全局一致性／覆盖 review，之后统一修订与复核，最后形成 WP80 净化规格集。执行细则见 §2.2；此前“先修 GR-011／GR-013 再继续新包”的建议不再作为当前执行顺序。

## 1. 提取顺序与依赖策略

1. **先固定证据与词汇。** WP01 确定 commit、缺失工程材料和未验证能力；WP02–WP08 提取配置、身份、内容、事件、时间/随机、诊断和本地化。世代设置、内容数据集和插件组合分别记录。
2. **建立生物与集合基础。** WP18–WP21、WP24–WP30 明确个体、状态、拥有者、队伍、盒子和道具边界。同步可处理持久化（WP09–WP10）及地图/输入基础（WP11–WP17）；这里的“同步”是工作顺序可独立安排，不要求创建并行 Agent。
3. **研究生命周期和世界情境。** 基础成长、寄养、遗传、孵化、时间/场地规则和普通遭遇在其依赖完成后提取。进化被拆为基础判定与跨域触发，避免迫使全部战斗先完成。
4. **战斗分层展开。** 先调查参战与阶段契约（WP39–WP42），再展开计算/状态/效果族（WP43–WP50）及 AI（WP51、WP52-A/B/C）。阶段契约可先引用具名但未展开的效果；WP42 的完整期限/时序规则仍需 WP44/45 的结果，不能把此路线当作严格完成顺序。
5. **组合功能分步闭合。** 捕获（WP38）、漫游/雷达（WP37）、战后进化（WP32）、Shadow（WP23）可以先研究已有输入支持的部分，再补齐专用状态、模式与时序引用。捕获无需等待全部效果或 AI；设施、特殊模式和录像依赖相关基础战斗行为。
6. **UI 随领域取证，随后完成流程审查。** 不等到最后才阅读 UI 文件，因为其中包含实际状态修改。WP65–WP67 的工作重点是可见性、选择、取消和跨页面返回；公式、容量等引用已完成领域规格。
7. **开发者/demo 与最后审查。** 编辑/转换工具在相应数据语义稳定后提取。WP77 追踪 demo 的配置—事件—能力链；之后依次做 WP78 一致性、WP79 覆盖和 WP80 sanitized 交付。

## 2. 每包共同完成标准

- 遵守根目录 `AGENTS.md` 的全部 clean-room 约束；不写框架代码，不复制参考表达式或逐行转述，不输出 Ruby/TypeScript API 或继承设计。
- 详细产物覆盖适用的目的、可见行为、概念、输入/输出、前置、状态变化、规则/不变量、边界/失败、依赖、配置、场景/测试、分类、问题和来源；不适用项说明理由。
- 搜索该主题的定义、调用者、配置、数据和 UI/事件消费者；记录实际查看的文件/片段及证据级别，不把目录存在当作实现证明。
- 每个领域记录基线默认行为、支持但未默认启用的变体、配置/数据/插件的关联及未验证组合；WP02 提供索引，各领域解释语义。参考行为、官方版本预期和未来目标取舍分开，不默认等同。
- 对随机行为描述输入分布/结果和验证条件，对确定性数值给出独立计算的测试向量。
- 至少提供正常、边界、失败或取消的适用场景；涉及容量、奖励、所有权或临时状态恢复时，说明一次操作前后的状态差异。
- 每包输出包括一份或一组范围明确的行为规格，以及 traceability、未决问题和对 Feature Matrix 的增量更新；维护 D → F → 规格/规则编号 → 证据与测试场景的链。证据区分已定位、静态确认、数据样本确认、运行确认与待验证（见总览），不与规格状态或置信度混同。建议目录仅沿用 `specs/kernel/`、`creature-rpg/`、`pokemon-rules/`、`combat/`、`overworld/`、`ui/`、`demo/`，不约束未来实现布局。
- 缺少运行材料时，可完成有静态证据的范围，明确标记待运行/待事件验证。不能把受阻部分算作完成，也不能为了补证修改当前 `reference/`。
- 表中的完成条件是在以上标准之外的重点验收点。若深入检查发现一个包仍含过多互不相同的规则族，先在计划和矩阵登记有界子包，再开始该子包；不要把未读部分笼统算作“同类已覆盖”。

## 2.1 包与功能状态的最小约定（2026-09-19，响应联合 review R02）

为分别表达“本包自身范围”“未闭合跨包引用”“外部 review 状态”和“Feature 聚合状态”，在不改动 18 领域、113 功能和 87 包编号的前提下约定以下最小规则。本节不新增平行追踪表；状态文字直接写在工作包登记、Feature Matrix 的 Specification status/Notes 和各规格文档头部。

1. **每包分开记录三类内容**：(a) 自身声明范围——本包独立成立、可按第 2 节标准验收的部分；(b) 必须满足的完成依赖——不闭合则本包范围不能判定正确的输入，未闭合时本包只能标 Partial 或 Blocked，不得仅为维持依赖无环而删除；(c) 后续扩展/复核引用（前向引用）——本包规则将被后续包补充、细化或复核的登记，每条注明目标包、规则主题、未闭合内容、影响范围和复核触发条件。
2. **前向引用不阻塞本包范围交付**：自身范围可独立成立且达到完成标准时，可先交付该范围并提交 review；但不得宣称依赖缺失规则的完整组合已经验证。例：WP43 可交付基础计算规格，同时登记“特性/道具修正项待 WP48/WP50 补充”的前向引用；WP30 可交付成长主规则，同时登记“Shadow 暂存与恢复细则待 WP23”的前向引用。
3. **包级规格状态取最小集合，且始终附范围**：**Drafted**（所述范围已提取并自检，待提交外部 review）、**ReviewPending**（已提交外部 review、等待结论）、**Reviewed**（注明范围经外部 review 通过；提取方自检不得标为 Reviewed）、**Partial**（范围内部分完成，须注明被阻塞的其余部分及原因）、**Blocked**（因未决依赖或材料缺口暂不能完成自身范围）。
4. **Feature 状态按承接它的包/子范围聚合表达**：同一 Feature 可同时持有不同范围的不同状态，禁止用单一笼统完成标记覆盖。例：F18-07 在 WP01 交付后可同时为“WP01 基线/缺口范围 ReviewPending”与“WP77 demo 验证范围 Provisional”。
5. **缺失 demo 不阻塞无关静态范围**：静态证据足以完成的范围可交付并送审；完整 demo 覆盖与事件可达性结论只能由 WP77 在获得事件证据后给出，两类结论分别记录。
6. **占位文件用途**：`planning/coverage.md` 预留给 WP79 覆盖审查表；`audit/source-traceability.md` 预留给 WP80 最终 traceability 索引；在此之前各包的 traceability 记录随各规格文档维护。

### 依赖与已知问题的处理

- **暂缓旧包返修**：已确认 GR、旧包新观察、通过后的管理性回填和独立批次整合统一保留待办，不再穿插反复的局部返修／复审循环。新提取所必需的最小当前登记仍照常维护。
- **读取已知问题，但不复制错误合同**：新包触及已知问题时，读取其具名源证据与已确认结论，注明上游规格尚待统一更正、规则归属和实际采用的临时依据。保留既有编号，不重复报同根因，也不在本阶段擅改旧主稿。
- **不能证明的范围如实保留**：缺少必需知识、demo／媒体或宿主证据时，明确受影响条款和未决前提，继续其它有独立证据的内容；不能删除真实依赖或把猜测写成已确认规则。
- **新稿自检仍必须完成**：明显笔误、遗漏的本包分支及与已读来源直接矛盾的内容，在本包自检时修正。延后的是集中外审与旧包统一修订，不是省略来源核对。

### 状态与汇报

新包默认标 **Drafted（提取与自检完成，待统一 review）**；若自身声明范围仍有无法闭合的必需部分，按 §2.1 标 **Partial／Blocked** 并列明范围。统一提交外审后才标 ReviewPending；未经独立审查不得自行标 Reviewed。
