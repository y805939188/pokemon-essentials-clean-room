## 1. 问题确认

旧 WP23 主稿第 134 行（§8.1 操作表「空位置从储存选择」）与第 215 行（W34）把「通用选择器正常可选队伍成员」与「下游放置／删除没有保留最后可战斗成员的守卫」混为一谈。WP66-B §2.2（已限定通过，`43a812fe…`／38,100）确认：通用选择入口以取出模式启动、不正常打开队伍面板；「队伍」按钮返回特殊位置 `[-2,-1]`，默认基础储存下指向零基盒 38 格 29。两处均修订为「正常 UI／特殊负位置／直接调用」三层合同。

## 2. 三层结论与证据

### 层次一：正常 UI 实际能返回什么

- 选择器以取出模式启动（`017_UI_PokemonStorage.rb:1964–2022` 的 `pbChoosePokemon` 以 command 1 开屏；`:912–913` 选择器直返盒选择结果），**队伍面板不作为正常入口打开**。
- 盒内网格选择返回 `[盒号, 格号]`；取消或 Close Box 确认后返回 **nil（不给位置，无写入）**；盒名进盒命令。
- 净化室侧的调用包装（`023_UI_PurifyChamber.rb:1273–1281`）只透传该返回值。
- 因此正常可提交给净化室放置的只有**盒内位置或 nil**；「通用选择可选队伍」不成立。

### 层次二：特殊负位置的来源与传播（不仅凭读取成功推断操作成功）

`[-2,-1]` 不是队伍语义；默认基础储存只有盒号 -1＝队伍，其它负盒号按数组末起寻址（`004_PokemonStorage.rb:159–176`），默认 40 盒配置下指向**零基盒 38 格 29**。各消费者分别消费：

| 消费点 | 格 38/29 为空 | 格 38/29 有成员 X |
| --- | --- | --- |
| 空位置放置（`023_UI_PurifyChamber.rb:400–408`） | 读得 nil → 放置直接 false、回编辑循环（无消息） | 经蛋／Shadow 门可实际放置 X，并 **`pbDelete(-2,-1)` 删除该盒格**（盒侧不压紧，`004_PokemonStorage.rb:254–259`） |
| 替换（`:497–512`） | 读得 nil → 无操作 | X 与室内当前成员的 Shadow **原始查询结果相等**（§8.1 替换门不变）时，**把室内当前成员写入该盒格**、X 进入室内 |
| 选择并暂持（`:525–528`） | nil → 无暂持 | X 被当作暂持来源 |

泄漏成员进入暂持／移动等**后续流程的行为未穷尽，具名保留、不称安全**；不给参考补「队伍面板可打开」的 UI 功能。

### 层次三：直接调用的下游合同（不得伪装成正常 UI 可达）

调用方不经选择器、直接提供**有效队伍位置** `[-1, 序号]`（脚本／调试等入口）时：放置读取该队伍成员、成功后 `pbDelete(-1, 序号)` 从队伍删除并压紧——**此链没有"保留最后可战斗队员"门**。该守卫只存在于 WP25 §5 的特定 UI 入口（PC 存入前置、仓库屏存入／拿起／释放守卫等），不在净化室放置、也不在容器删除本身。**此合同成立，但不得作为正常选择 UI 的可达示例；也不能用它证明正常 UI 能取得队伍位置。**
